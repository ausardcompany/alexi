## Critical (block)

### C1 -- `--yolo` deny-list bypass: case sensitivity + missing dot-escape + no keyword coverage (UNRESOLVED CARRY-OVER, week 5)

- Files:
  - `src/permission/allow-everything.ts:53-56` -- `matchesPattern()`
    naive glob-to-regex converter.
  - `src/permission/index.ts:375-393` -- `getAllowEverythingDelegate()`
    that seeds excludes from the `deny-secrets` rule.
  - `src/permission/index.ts:974-980` -- the `deny-secrets` rule
    payload (`paths: ['**/.env', '**/.env.*', '**/secrets.*',
    '**/*credential*', '**/*secret*']`).
- Bug (unchanged for four consecutive audits): `matchesPattern` does
  `new RegExp(pattern.replace(/\*/g, '.*'))`. This is case-sensitive by
  default, does not anchor with `^` / `$`, and does not escape the `.`
  metacharacter. On Linux (the actual runtime for `alexi-bot`) this
  produces three bypasses in `--yolo` mode:
  1. Case-only variants of `**/.env` (`.ENV`, `.Env`) do not match the
     regex because `.env` literally maps to `.*/.env` case-sensitively.
     A tool run in `--yolo` mode can therefore read a file literally
     named `.ENV` on a case-preserving filesystem.
  2. The pattern `**/.env.*` expands to `.*/.env..*` (unescaped dot),
     which matches `.envXlocal` (benign false-positive) but does NOT
     match `foo.env` -- meaning a co-located `env.json` /
     `dev.env.local` variant would slip through if renamed.
  3. `**/*credential*` / `**/*secret*` are literal substring keywords
     only -- they miss the SAP-specific token `AICORE_SERVICE_KEY*`
     (uppercase, contains neither `credential` nor `secret`), the
     GitHub token pattern `ghp_*` / `github_pat_*`, `NPM_TOKEN`, and
     `SAP_PROXY_*`. The belt-and-braces `**/.ssh/**` clause in
     `src/permission/index.ts:387` correctly catches SSH keys, but
     there is no equivalent belt-and-braces for the SAP secrets.
- Severity: `block`. `--yolo` is opt-in on the CLI but is wired into
  agent workflows via `--auto` / `--dangerously-skip-permissions`
  (referenced from `AGENTS.md` under "Tool harness"). A prompt
  injection that convinces the agent to read `AICORE_SERVICE_KEY.json`
  will succeed in `--yolo` mode today. The 2026-09-21 audit escalated
  this to critical; it is still critical.
- Recommended fix (unchanged; owner: `role-security` +
  `role-engineering`):
  1. In `src/permission/allow-everything.ts:53-56`, replace
     `new RegExp(pattern.replace(/\*/g, '.*'))` with `matchPattern`
     from `src/permission/wildcard.ts:62` (which already handles `**`,
     escaping, and anchoring) OR reuse `matchesPattern` from
     `src/permission/next.ts:2`. Do NOT re-implement glob-to-regex a
     fourth time.
  2. In `src/permission/index.ts:375-393` extend the belt-and-braces
     block to add `AICORE_SERVICE_KEY*`, `SAP_PROXY_*`, `NPM_TOKEN*`,
     `GH_PAT*`, `**/*.pem`, and `**/*.key`.
  3. Add regression tests to `src/permission/allow-everything.test.ts`
     (create if absent) covering case-only variants, `foo.env`,
     `AICORE_SERVICE_KEY.local`, and a `.PEM` file.

### C2 -- `xlsx@0.18.5` prototype pollution + ReDoS, no upstream fix (UNRESOLVED CARRY-OVER)

- Advisories via `npm audit --omit=dev`:
  - `Prototype Pollution in sheetJS`
  - `SheetJS Regular Expression Denial of Service (ReDoS)`
- `range: "*"`, `fixAvailable: false`. SheetJS has moved fixes to a
  paid-only distribution channel (`https://cdn.sheetjs.com/`).
- Files: `xlsx@0.18.5` is a **direct** dependency in `package.json`.
  A repo-wide grep confirmed there is currently NO import of `xlsx`
  under `src/` (`grep -rn "from 'xlsx'\|require('xlsx')\|from
  \"xlsx\"" src/` returns zero hits). This means the CVEs are unreachable
  from runtime code today, but the vulnerable version is still
  installed on every CI runner and every user machine that runs
  `npm ci`, and any future feature that imports `xlsx` inherits the
  RCE surface silently.
- Severity: `block`. A prod dependency with `fixAvailable: false` for
  a prototype-pollution CVE cannot sit at `severity: high` forever
  without a plan.
- Recommended fix (unchanged from 2026-08-24):
  - Preferred: replace with `exceljs` (`^4.4.0`), which has an active
    security channel and a similar API. Owner: `role-engineering`.
  - Fallback: remove `xlsx` from `package.json` entirely since nothing
    in `src/` imports it. This is a one-line PR that closes both CVEs
    permanently. Owner: `role-security`.

### H4 -- `.github/workflows/security.yml` audit gate is toothless (UNRESOLVED CARRY-OVER)

- File: `.github/workflows/security.yml:24-25`.
- Bug: `npm audit --audit-level=high` runs with `continue-on-error:
  true`. The weekly job therefore prints the finding count but always
  passes green, so branch protection is meaningless and the H3-class
  findings have accumulated for at least four weekly cycles.
- Severity: `warn`. CI hygiene finding, not a code CVE, but it
  directly explains why C2 and H1--H3 have gone unaddressed.
- Recommended fix: remove `continue-on-error: true` on
  `.github/workflows/security.yml:25` and set `--audit-level=critical`
  so the job only fails on `critical` findings. Documented exceptions
  (C2, H1, H2) can then be handled via `npm audit --json | jq`
  filtering in a small script step, OR by keeping the current
  `--audit-level=high` and simply removing `continue-on-error` once
  C2/H1/H2 are actually fixed. Do NOT paper over with
  `npm audit --production` on top of `--omit=dev`. Owner:
  `role-infrastructure` (already assigned in 2026-09-21 audit).

### H5 -- `release.yml` still calls `npm ci` without `--ignore-scripts` (UNRESOLVED CARRY-OVER from 2026-06-22 W4)

- Files: `.github/workflows/release.yml:34` and `.github/workflows/release.yml:87`
  (both `run: npm ci`, no flags).
- Attack: the release pipeline runs `npm ci` in a fresh runner that
  will later see publish credentials (`NPM_TOKEN`) and repo write
  (`GH_PAT`). A malicious `postinstall` script in any transitive
  dependency would execute inside the release runner with access to
  those secrets before the publish step masks them.
- Severity: `warn` -- lockfile drift is monitored by encoding-guard
  and by daily-merge, but this remains a documented residual risk.
- Recommended fix: change both `run: npm ci` lines to
  `run: npm ci --ignore-scripts`, and if any dependency's `postinstall`
  is required for the release artefact, invoke that build step
  explicitly (e.g. `npx tsc-files --project tsconfig.json` for
  `tsc-files`, or the affected package's documented build command).
  Also consider migrating the release job to a dedicated `release`
  environment with an `environments.protection_rules` gate so a human
  approves publish. Owner: `role-infrastructure`.
