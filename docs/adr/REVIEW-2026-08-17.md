### F23 `warn` -- NEW: dead re-export chain `src/tool/grep.ts` -> `src/tool/grep-signal-controls.ts`

`src/tool/grep.ts` used to be a 27-byte F16-family comment shim.
This cycle it grew into a 19-line re-export module:

```ts
export {
  applySignalControls,
  type GrepMatch,
  type GrepSignalControls,
} from './grep-signal-controls.js';
```

The header comment states this is "the plan-anchored surface for the
upstream #12811 grep signal controls" so callers can wire signal
filtering "without reaching into the tool internals."

Consumer scan:

- `grep -rn "from ['\"][^'\"]*tool/grep\.js" src/` (excluding
  `tools/grep`) -> zero.
- `grep -rn "grep-signal-controls" src/` -> exactly one hit, the
  re-export inside `src/tool/grep.ts` itself.
- `grep -rn "applySignalControls\|GrepSignalControls\|GrepMatch"
  src/` -> zero outside the two files.

So the entire chain `grep.ts (re-export) -> grep-signal-controls.ts
(implementation)` has zero consumers. Combined LOC:
`19 + $(wc -l < src/tool/grep-signal-controls.ts)` = ~90 lines of
dead exports. The actual grep tool at `src/tool/tools/grep.ts` does
not go through this "plan anchor" -- it wires `ripgrep` fast-path
and the JS fallback directly.

This is a graduation from F16 (comment shim) into a *new* dead-
export category. Not progress -- the file is still not solving a
problem, it is just louder about not doing so.

Severity `warn`. Recommended fix: either wire the signal controls
into `src/tool/tools/grep.ts` in a follow-up PR (making
`grep-signal-controls.ts` actually load-bearing), or delete both
files in the same subtractive cleanup PR that closes F10/F11/F13/F16.

Note: `src/tool/warpgrep.ts` also grew from 35 B (F16 shim) to
